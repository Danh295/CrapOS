Real mode, the BIOS menu, and your puts

Lesson 1 · about 20 minutes · goal: explain every line of puts and why it misbehaves.

The win: by the end you can say what int 0x10 does, how the CPU turns 07C0:0000 into an address, and why your first boot printed nothing.

1. Real mode: what the CPU is doing when your code starts

Every x86 CPU starts in real mode, the original 8086-era mode. It has a 20-bit address space, which gives 1 MB of addressable memory, and it has no memory protection, no multitasking and no privilege levels. The PC BIOS runs in real mode, and so did DOS. [Wikipedia: Real mode]

Registers are only 16 bits wide, which can reach 64 KB. To reach 1 MB, an address is built from two 16-bit parts. The CPU shifts the segment left by four bits and adds the offset:

physical = segment × 16 + offset

0000:7C00  →  0x00000 + 0x7C00 = 0x07C00
07C0:0000  →  0x07C00 + 0x0000 = 0x07C00   (same place, different spelling)

That's why your code says mov ax, 0 / mov ds, ax before touching msg_hello: ds is the segment that every plain data access uses. Many segment:offset pairs name the same byte. Each segment can reach only 64 KB, because the offset has 16 bits. (That last point is my inference from the 16-bit offset, not a quote from the source.)

The CPU sees segment 0x1000 and offset 0x0020. What physical address is that?

2. The BIOS menu

The BIOS is firmware that ships with the machine. It stays in memory and offers services you can call. You call one with the INT instruction: the number after int says which group of services you want, and the value you put in AH says which function inside that group. Inputs and outputs mostly travel in registers. [Wikipedia: BIOS interrupt call]

CallGroupYou'll use it for
int 0x10VideoPrinting characters. This lesson.
int 0x13DiskLoading the second stage from the floppy. A later lesson.
int 0x16KeyboardReading what the user types. A later lesson.

Why not use this menu forever? Modern operating systems stop calling the BIOS after startup. BIOS code only runs in real mode, so switching modes for every call is slow, and it can't reach much memory. That's a constraint of your chosen rung, not a flaw in your project.

3. One character at a time: int 0x10, AH=0x0E

Within the video group, function 0x0E is teletype output: it prints the character in AL at the cursor and moves the cursor on. BH picks the display page. BL is a color but only matters in graphics modes. It returns nothing. [Ralf Brown's list, Int 10/AH=0Eh]

The key word is one. The BIOS has no "print a string" call here. If you want "Hello world!", you have to call it twelve times, once per letter. That's what puts is for.

4. What puts actually is

puts isn't part of the BIOS. It's a subroutine you wrote in src/main.asm, named after the C function that prints a string. It wraps the one-character BIOS call in a loop. Read it against the source:

InstructionWhat it does
push si / push axSaves the caller's registers on the stack so puts can borrow them.
lodsbLoads the byte at DS:SI into AL, then adds 1 to SI. After this, SI points at the next character.
or al, alORs AL with itself. The value doesn't change, but the zero flag is set if AL was 0. This is the cheapest "is it zero?" test.
jz .doneIf it was zero (the string's null terminator), leave the loop.
mov ah, 0x0e / mov bh, 0 / int 0x10Function 0Eh, page 0, and call the BIOS to print the character that lodsb put in AL.
jmp .loopGo around again for the next character.
pop ax / pop siRestores the saved registers in reverse order.

The calling convention is in your own comment: the caller puts a pointer to the string in ds:si, and main does that with mov si, msg_hello before call puts.

Open this only after you've answered in chat (a measurement, not a hint)

When I built this repo, build/main.bin came out at 527 bytes instead of 512. The string Hello world! sits at file offset 0x200, which is after the 55 AA signature. In QEMU, the boot sector was loaded at 0x7C00 as expected, but the memory at 0x7E00, where the string would be, was all zeros. The BIOS only copied one 512-byte sector into RAM, so the text never made it there.

Booting this printed nothing, and the CPU kept running near 0x7C1F. There's a second bug in the code that explains the "kept running". I'm not telling you what it is. Find it using the table in section 4.

Why this matters for CrapOS: the BIOS gave you 512 bytes, and your program already doesn't fit. A second stage, which the first sector loads from disk with int 0x13, is the way out. That's the rung you chose.
